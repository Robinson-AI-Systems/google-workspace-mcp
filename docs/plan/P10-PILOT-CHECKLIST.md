# P10-6 — safe Google Console setup and two-user pilot preflight

This is an operator procedure for the **existing** P10-6 acceptance card, not new product scope. The owner approved one non-billable two-user sign-in pilot on October 17, 2026. That did **not** approve a manual release, public launch, paid service, broader Google scopes, production writes, or retirement of the existing owner sign-in. The existing owner Google OAuth app is never modified or reused.

## Google Console: distinct public application

1. Create a **separate** Google Cloud project/application for this product. Choose Google Auth Platform **External / Testing** for the bounded pilot and keep the existing owner's project, callback, grants and client credentials unchanged. If Google Console shows other registration, verification or organization prerequisites, record actual evidence rather than guessing.
2. Configure app branding, support email, intended homepage, data-use/privacy page and the deletion process. The public source pages for this service are `<PUBLIC_BASE_URL>/`, `<PUBLIC_BASE_URL>/api/privacy`, `<PUBLIC_BASE_URL>/api/support`, `<PUBLIC_BASE_URL>/api/data-deletion`. These are truthful *prelaunch information pages*, not an operator-reviewed legal policy or evidence of Google brand approval.
3. Google requires a public app homepage on a domain the operator can verify, matching the configured privacy URL and application identity. A default provider-owned `.vercel.app` subdomain **might not satisfy domain ownership verification** for general public verification; inspect Google's actual domain ownership result and move to an owned verified hostname if required. Do not silently change `PUBLIC_BASE_URL` without also changing the callback and registered MCP resource.
4. Create an OAuth **Web application** client with the exact registered callback `<PUBLIC_BASE_URL>/api/auth/google/callback`. Save the new client ID and client secret **directly** into Vercel production under `PUBLIC_GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_PUBLIC_OAUTH_CLIENT_SECRET`. Do not paste secrets into chat/GitHub or replace `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET`. In Vercel Production, store the client ID using type **Config** and the server-only `GOOGLE_PUBLIC_OAUTH_CLIENT_SECRET` using type **Secret**. Vercel rejects Secret types with public framework prefixes; do not try to save the OAuth client secret under `PUBLIC_` or downgrade its visibility to Config. Set an owner-reviewed `PUBLIC_SUPPORT_EMAIL` as Config for the public contact page.
5. Start with Google identity scopes `openid email profile` only. The actual optional mail/files/calendar/tasks/contacts/adminVerify groups are taken from source `src/principals/google.js` and displayed by the protected readiness report. Declare **only the scopes actually requested** by an intended workflow. Google may require brand/sensitive/restricted verification or a third-party assessment for general publication; testing and certain narrow circumstances may qualify for an exception. This is Google's decision, not a developer-imposed permanent limit. Do not purchase or submit a review contract without owner approval.
6. Add the two owner-authorized disposable Google test accounts in the Google Auth Platform testing users list. This is an **email list in Google Console**, distinct from the server's pilot subject-ID allowlist. A test user's typed email, hosted domain or admin hostname never substitutes for a verified OIDC subject.

## After an authorized checked release (public still OFF)

- Open `<PUBLIC_BASE_URL>/api/owner/pilot-readiness` at the **canonical HTTPS hostname**; authenticate with the existing owner `ADMIN_PASSPHRASE`. This read-only report describes current source scopes, missing configuration, and external checks. It contains no bearer, client secret, passphrase, private mailbox, or subject ID. A green-looking configuration report never claims a real provider pass.
- Use the **Google-verify a pilot tester (no enrollment)** button twice, each time signing into the correct disposable Google testing identity in the separate OAuth app. The existing passphrase protects the start, and the actual verified Google OIDC result is bound to one transaction and browser cookie. The post-verification page shows the Google subject ID only in the protected browser, with no token/grant/user creation. Record subject IDs directly in protected Vercel `PUBLIC_PILOT_GOOGLE_SUBJECTS` (comma separated). Do not copy them into a chat, issue or code. A subject ID does not confer customer administration.
- Keep `PUBLIC_SIGNIN_MODE=off`, `PUBLIC_P10_TOOL_EXECUTION_VERIFIED` unset/false and `LEGACY_OWNER_SIGNIN_ENABLED=true` throughout preflight and subject discovery. Verify the current serving READY source and direct original-owner Workspace `whoami`/account-list read before any **identity-only Stage 1** change. Do not rotate, revoke or silently migrate original owner bearer/refresh credentials. The original owner bearer/refresh replay and Hub TEST identity/read-only denials must still be independently proved to close `P10-OWNER-CONTINUITY`, but are **not** preconditions for two verified testers' standalone Workspace-only sign-in. See the owner decision dated 2026-10-17 in `docs/PUBLIC-SIGNIN-OWNER-GUIDE.md`. A plain Vercel READY status alone is not sufficient for Stage 1.
- **Stage 1 only, explicitly approved 2026-10-17:** After the checked READY source and direct-owner readback, confirmed separate OAuth app, two verified subject IDs, and existing principal/DB isolation source proof, set **only** `PUBLIC_SIGNIN_MODE=pilot` on Vercel Production. Leave `PUBLIC_P10_TOOL_EXECUTION_VERIFIED` unset/false, legacy owner sign-in available and all other credentials unchanged. Do **not** assume that updating Vercel env triggers a rebuild. Verify an actual fresh Vercel Production deployment (only through a normal scheduled checked release or a separately explicitly owner-approved off-cycle deployment/redeployment of the exact verified SHA), canonical alias, protected pilot-readiness counts/mode/flags, and direct owner readback afterward; then test two independent Google browser sessions, wrong-subject refusal and logout. Do not call this full pilot acceptance. **Stage 2 and complete original acceptance** separately require the full P10-C account isolation, original bearer/refresh and Hub-specific continuity, two distinct real MCP clients, principal/account boundaries, wrong-account refusal, replay/CSRF and refresh denial, proper revocation, cleanup and separately approved read/write execution. The existing `P10-VERIFY-GOOGLE`, `P10-MCP-PILOT`, `P10-OWNER-CONTINUITY` acceptance rows must still receive authentic source-pinned results.
- A reversible non-billable provider **write** is a separate action with its own target, risk, consent, exact request and cleanup. The owner approved the pilot, not an unspecified provider write. Likewise customer Domain-Wide Delegation and any licensing charges need their own original approvals.
- No source build, scope listing, settings flag, pilot subject probe, test fixture or Google Console screenshot can be marked as completed provider/public acceptance without the original runtime evidence.
